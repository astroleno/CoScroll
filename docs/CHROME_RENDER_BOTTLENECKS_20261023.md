# 独立 Chrome 复测与保留画质的优化方案

日期：2026-10-23。范围：复测当前线上版本，分别测量玉石透射、背景与 CSS 遮罩，提出可评审的优化方案。本次未修改产品源码、构建、提交或部署。

## 结论

1. **当前线上版本没有在本次独立 Chrome 测试中被固定限制为 30 FPS。** 正文连续播放 60 秒，rAF 平均 60.03 FPS，最大帧间隔 17.7 ms；后续浏览器合成追踪也记录到约 60 FPS 的实际呈现。
2. **玉石透射是已确认的主要 GPU 开销。** 手机视口三组配对实验，关闭透射后主场景 GPU 计时均下降，幅度为 52%–73%。这是定位实验，关闭透射会改变玉质，不作为交付方案。
3. **背景占用次要但真实的 GPU 资源；遮罩增加合成工作。** 两者本次都没有造成稳定的 30 FPS。WebGL 计时与浏览器合成计时属于不同范围，不能简单相加。
4. **优先建议保留完整透射缓冲区，只缩小每帧清除和解析更新的区域。** 临时原型三组配对中，主场景 GPU 均下降，平均从 9.04 降至 7.49 ms，约 17.1%；固定画面比较完全一致。不过原型增加了 CPU 开销，且只验证了一个字模，尚不具备直接上线条件。

这些结果不能替代真实手机测试，也不能单独解释此前 Ego 环境的 30 FPS。浏览器、电源与系统负载等条件已经不同；本次正常播放及 4 倍 CPU 限速的正文压力窗口均没有重现此前约 1 秒的停顿。

正常播放和纯 CSS 对照各测 6 × 10 秒。分项测试先获得桌面尺寸的 3 组配对，再显式固定手机视口，获得 3 组 × 每项 8 秒的配对数据。每次切换先预热。桌面与手机数据分开统计，没有混合计算。

测量使用 `EXT_disjoint_timer_query_webgl2` 记录 WebGL GPU elapsed time，同时记录主线程 render 耗时、绘制次数、解析与 mipmap 次数、rAF、可见性及错误。所有分项开关仅用于临时页面诊断，结束后恢复。GPU elapsed time 会受队列竞争和设备频率影响，表示该命令区间的耗时，不能当作硬件核心利用率或独立阶段的可加总预算。

## 1. 当前版本的帧率

| 测试 | 总时长 | 平均 rAF FPS | 最大帧间隔 |
|---|---:|---:|---:|
| 同一独立 Chrome 的纯 CSS 动画对照 | 60.07 秒 | 59.28 | 34.2 ms |
| 当前线上正文连续播放 | 60.07 秒 | 60.03 | 17.7 ms |
| 正文压力窗口：CPU 4 倍限速、4 Mbps、80 ms 延迟 | 60.08 秒 | 60.02 | 17.8 ms |

正常正文窗口的各组 P95 帧间隔为 17.0–17.5 ms，压力窗口各组为 17.5 ms；两者均没有记录到 long task、long animation frame 或页面错误。压力测试在资源已加载的正文中进行，不能用来推断冷启动耗时，也没有模拟真实手机 GPU 的性能。

rAF 本身不能证明每帧都已显示，因此另取 6 个浏览器追踪窗口。保留遮罩和移除遮罩各约 18 秒，`Display::FrameDisplayed` 平均均约 60.00 FPS；已记录的 `PipelineReporter` 状态均为 `STATE_PRESENTED_ALL`。有一组包含 33.33 ms 的呈现间隔，不能据此宣称“绝对零掉帧”。

因此，目前证据支持“当前版本在此 Chrome/M4 条件下可以达到 60 FPS”，不支持“某个产品代码固定把帧率锁在 30”或“真实手机已全部达到 60”。

## 2. 三个部分的成本

以下数字是手机视口各组窗口均值，再对三组等权平均。各项采用各自相邻基线，基线差异反映系统波动。

| 临时定位操作 | 配对基线：主场景 GPU | 操作后：主场景 GPU | 解释 |
|---|---:|---:|---|
| 透射从 1 改为 0 | 7.82 ms | 2.93 ms | 三组下降 52.2%、58.9%、72.9%；同时去掉透射预绘制与外层透射着色，不能把全部差额称作预绘制成本 |
| 背景停止更新、保留其 Canvas 和最后画面 | 10.30 ms | 7.87 ms | 背景自己的 GPU 均值约 1.19 ms；主场景也变快，说明存在共享 GPU 竞争，不能相加得到“背景总成本” |
| 移除 CSS 遮罩 | 10.09 ms | 9.47 ms | 主 WebGL 查询不包含 CSS 合成，因此 0.62 ms 差额不是遮罩的精确 GPU 成本 |

桌面尺寸的透射实验同样三次明显下降：主场景窗口均值平均 15.62 → 6.54 ms。桌面遮罩实验的方向不稳定，进一步说明不能用主 WebGL 查询推算 CSS 遮罩开销。

分项基线中主场景 `render()` 的 CPU 均值约 0.27–0.35 ms；固定暂停场景没有 React commit。这里能确认稳态压力主要在 GPU 路径，不能据此排除拖拽、切换模型或首次加载时的 CPU 问题。

### 透射的具体路径

线上实际使用 Three 0.160.1 的完整透射路径。实测透射目标为主场景全尺寸、HalfFloat、4 samples、生成 mipmap。每次主场景渲染产生一次 `blitFramebuffer` 和一次 `generateMipmap`；关闭透射时两者均归零。

源码显示，透射预绘制绘制 opaque 列表；当前主要是内层玉石。透明歌词不在该预绘制列表中。随后主画面再次绘制不透明对象、外层透射对象和透明歌词。

保持全部画质，分别对内部阶段做两次 5 秒测量：

| GPU 查询范围 | 两次窗口均值 |
|---|---:|
| 完整主场景 | 9.46 / 8.71 ms |
| 透射预绘制至解析、mipmap 完成 | 6.58 / 2.76 ms |
| 其中的多重采样解析 `blitFramebuffer` | 3.62 / 2.28 ms |
| 其中的 mipmap 生成 | 0.76 / 0.30 ms |
| 外层玉石绘制 | 5.70 / 5.59 ms |

这些阶段来自不同时间窗口，预绘制也包含后两项，不能求和。波动较大，但足以把进一步优化集中到**透射缓冲区的处理和外层着色**，而不是播放器 React 更新或增加 `powerPreference`：R3F 已默认请求 `high-performance`，本次两个真实 context 也均如此。

### CSS 遮罩的合成成本

6 次 Chrome 追踪采用交替顺序，使用同一场景和绘制尺寸：

| 追踪指标 | 保留遮罩 | 移除遮罩 |
|---|---:|---:|
| 实际呈现平均帧率 | 60.00 FPS | 60.00 FPS |
| `DirectRenderer::DrawFrame` 平均线程 CPU 时间 | 0.220 ms/次 | 0.043 ms/次 |
| 合成 GPU 线程执行任务的 CPU 时间，按显示帧数归一 | 1.016 ms/帧 | 0.359 ms/帧 |
| `FinishPaintRenderPass` 事件 | 约 2 次/帧 | 本窗口为 0 |

第二、三行存在包含关系，不能相加；“合成 GPU 线程 CPU 时间”也不是物理 GPU 执行时间。结果确认遮罩产生额外离屏合成工作，但没有证据把它认定为本次帧率瓶颈。整层 CSS 遮罩作用于已经合成的模型与歌词，不能直接用每个字的透明度羽化替代而声称等价。

## 3. 保留画质的候选验证

### 首选：保持完整缓冲区，只更新发生变化的区域

临时原型没有缩小纹理尺寸，没有减少 MSAA，没有删除 mipmap，也没有修改物理材质。它做了以下操作：

1. 投影当前内层玉石的保守包围盒，扩展抗锯齿边界。
2. 合并本帧与上一帧覆盖区域，确保旧位置被正确清除。
3. 首帧执行完整更新；之后只在合并区域清除、绘制并做多重采样解析。
4. 仍对原尺寸纹理执行完整的原生 mipmap 生成。区域外保留正确的背景清除值，折射仍可采样完整纹理。

三组测量的主场景 GPU 均值：

| 配对 | 完整更新 | 区域更新 | 降幅 |
|---|---:|---:|---:|
| 1 | 9.18 ms | 7.52 ms | 18.0% |
| 2（反向顺序） | 9.43 ms | 8.48 ms | 10.1% |
| 3 | 8.52 ms | 6.47 ms | 24.0% |
| 三组平均 | **9.04 ms** | **7.49 ms** | **17.1%** |

原型平均更新约 26.9% 的区域。背景与模型 0°、90°、180° 共四张固定帧比较，所有通道差异均为 0；材质参数、context 属性和绘制尺寸一致，两个 Canvas 保留，无页面错误。

**限制：**原型为了验证边界，每帧读取 GL 状态并创建临时对象，主场景 CPU 均值约 0.42 → 1.07 ms。产品实现必须消除这些同步状态读取和重复分配。这只是一个字模、一个视口下的候选证据，不代表全模型、全设备验收完成，也不能承诺 FPS 增加 17%。

### 不纳入优先方案：只省略未使用的深度解析

确认当前透射纹理没有深度采样后，临时让解析只复制颜色，保留绘制时的深度测试与 4 samples。四张固定帧也完全一致，但三组主场景 GPU 均值约 8.15 → 8.27 ms，方向不稳定。此优化在本环境没有收益证据，不为它单独引入依赖内部实现的代码。

## 4. 建议的实现设计与验收

### 第一阶段：把区域更新做成可回退的透射优化

目标是减少全屏缓冲区的重复清除与解析，同时维持双 Canvas、当前材质、几何、HDR、DPR、4 倍抗锯齿和完整 mipmap。

| 模块 | 建议职责和接口 |
|---|---|
| 新增 `src/rendering/transmissionUpdateRegion.ts` | 计算并复用 `PixelRect`，管理上帧区域、目标尺寸和失效状态；`update(objects, camera, bufferSize)` 返回保守矩形或完整更新标志；`reset()` 用于重建、切换和恢复 |
| `src/components/layouts/UnifiedLyricsAndModel.tsx` | 主场景生命周期接入；继续保留现有主 Canvas、全部图层与 CSS 遮罩 |
| `src/components/jade/JadeModelLoader.tsx` | 提供实际已显示模型和变换信息；模型替换、重置、材质/环境变化时使区域状态失效，不改变模型发布顺序 |
| 固定版本 Three 的小范围适配 | 只给透射预绘制和解析增加可选更新矩形；默认仍为完整更新；正常主场景和其他渲染目标的行为不变 |
| 性能及视觉验证工具 | 保存版本、实际尺寸、GPU 查询、呈现事件和固定帧；测试开关不进入用户界面 |

实现约束：

- 区域使用实际 drawing buffer 像素坐标，不能混用 CSS px 或重复乘 DPR。
- 包围范围必须覆盖本帧和上帧。首次使用、resize、context 恢复、相机变化、模型替换及边界不确定时，回退整幅更新。
- 对当前未验证的多不透明对象、特殊材质、副作用或透视裁剪情况，先走原始完整路径。不能把单字原型的假设默默推广到所有场景。
- 保留完整纹理及其所有 mip 层；不得通过缩小纹理、减少采样或改写粗糙度/折射公式来凑性能收益。
- 在渲染器内部维护、恢复 scissor 状态，不采用原型中的全局方法替换、每帧 `getParameter` 或不断分配数组。
- 固定 Three 版本并为适配增加行为检查，不能直接长期修改 `node_modules` 后依赖本机状态发布。

验收门槛：

1. 原始路径与优化路径都有开关，失败可完整回退；WebGL1/不支持能力的环境走原路径。
2. 两首内容、全部正式字模；正面、侧面、背面、任意旋转；最细笔画、大包围盒及视口边缘均覆盖。先以逐像素一致为目标；非零差异必须定位，不能默认视为无损。
3. 验证歌词前后遮挡、整层边缘遮罩、调色、播放/暂停、快拖、切换、循环、resize、前后台恢复与资源释放；没有残影、旧区域污迹或状态泄漏。
4. 至少 3 组交替顺序、各 30 秒的配对 GPU 测量，以及正常播放和快速交互各 60 秒的呈现追踪。建议以主场景 GPU 中位数改善至少 10%、P95 不恶化作为保留候选的门槛，不作为已达成结果。
5. 消除原型的 CPU 代价；CPU P95、长帧及资源数量不得回归。真实 iPhone/Safari、Android/Chrome 分别验证，不用 M4 尺寸模拟替代。

### 第二阶段：按剩余成本选择，不同时改三条链路

- **外层着色：**若第一阶段后仍有 GPU 压力，再检查模型尺度、视图投影矩阵等逐片元不变的计算能否按对象预计算。保留现有物理公式、法线、粗糙度变化和双三次纹理采样。现有 `specializePhysicalMaterial` 已做一批常量化，不能把重复设置参数当作新优化。
- **背景：**保留原分辨率与运动节奏。可验证稳定的 UV 旋转和尺度计算是否能移至顶点阶段，或显式创建不透明背景 context 是否有合成收益。Three 0.160.1 内部创建 context 时使用 `alpha: true`，所以只在现有配置写 `alpha: false` 不足以证明实际 context 不透明；本次真实属性确为 true。此项需单独 A/B 和像素验证，收益尚未测定。
- **遮罩：**目前维持原样。若目标真机追踪证明合成占主导，再评估等价的最终画面遮罩；不要提前添加新的离屏通道，也不要把单个字的透明度替代为整幅合成后的遮罩。

不建议在此方案中降低 DPR、关闭抗锯齿、冻结背景、合并 Canvas、取消透射或换成近似折射 shader。它们不满足当前确认的画质与双 Canvas 约束。

## 5. 证据与可复核文件

数据来自本机独立 Chrome 对当前公开页面的运行测量，以及项目锁定版本的实际源码；没有使用其他项目或私人历史数据。下列文件名记录测量时的来源；后续按用户要求清理了截图、原始大体积追踪、测试浏览器和临时构建，保留小型结果 JSON 与脚本。

- 原始结果目录：`../.cache/chrome-isolation-20261023/`。
- `baseline-visible.json`：纯 CSS 与当前线上正文各 60 秒。
- `pressure.json`：CPU 4 倍限速、4 Mbps、80 ms 延迟的正文 60 秒；结束后恢复限速设置。
- `components.json` / `components-mobile.json`：桌面与手机视口独立的分项 A/B，含逐帧间隔、GPU/CPU、GL 调用与恢复检查。
- `pass-trace.json`：完整画质下的透射阶段计时；末尾首次 tracing 参数组合被协议拒绝，该失败不计入测量，合成追踪由下一文件独立完成。
- `mask-trace.json`、`trace-0-baseline.json` 至 `trace-5-mask-off.json`：六组实际浏览器合成追踪；`analysis.json` 保存汇总。
- `depth-resolve.json`：没有稳定收益的深度解析实验。
- `transmission-region.json`：区域更新候选的三组配对、像素比较、CPU 代价和恢复检查。
- `gpu-system.json` / `browser.json`：浏览器版本、硬件与启动参数。
- 透射实现依据：`node_modules/three/src/renderers/WebGLRenderer.js` 的 `renderTransmissionPass`，`WebGLTextures.js` 的 `updateMultisampleRenderTarget`，以及 `transmission_pars_fragment.glsl.js`。
- 追踪字段使用 Chrome 官方 [DevTools Protocol Tracing](https://chromedevtools.github.io/devtools-protocol/tot/Tracing/)；帧状态直接取自本次 trace，未用 rAF 代替呈现状态。

本报告记录实现前的复测、分项归因和优化提案。后续区域更新实现与全模型回归结果见 [区域更新验证记录](TRANSMISSION_REGION_VALIDATION_20261023.md)；真实手机验证及此前环境特有卡顿的最终归因仍有缺口。
